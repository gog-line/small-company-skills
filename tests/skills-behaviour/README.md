# Skill behaviour runs (S4)

Evidence for L3: the same skill in PL and EN, given the same inputs, has to take the same steps, block on the same gaps and return the same shape of result.

- **Cases:** `cases/<skill>/<case>/task.{pl,en}.md` with `cases/<skill>/<case>/artifacts/` next to it. Each task invokes the skill explicitly and holds no expected answer.
- **One artifact set per case (S5 R2, R7).** A case holds only what it is meant to give: the PM `missing-input` set has no source of the project goal at all, and the withheld input is never named by a file name — every review package is `package.md`. Which input was withheld is known to the judge, not to the run. The two review tasks `valid` and `missing-input` are now word for word the same; only the package in the workspace differs.
- **The input gate runs before every run:** `node scripts/artifacts.mjs <case-dir>` (called by `run.sh`, exit 3 stops the batch). It checks the declared set in `inputs.txt` against what is on disk, refuses a file nobody declared, an empty file, a task that names an artifact the set does not hold, a hash in the package that does not match the file, and any `*.patch` that `git apply --check` rejects. It exists because the S4 review diff was not a valid patch and nothing noticed until the reviewer did.
- **Artifacts are deliberately in one language (English) and identical for PL and EN.** The only variables are the language of the skill and of the task prompt. Translated data would add a third variable, the quality of the data translation. English technical data is also the common case in real work.
- **Tools, a closed allowlist:** `--tools "Read,Glob,Grep"` is the whole tool set (host `init` event: exactly these three, in all 12 runs, with an empty MCP list). A denylist is not enough: it left `SendMessage`, `CronCreate`, `Monitor`, `PushNotification` and `RemoteTrigger` within the model's reach. The skill loads from the slash invocation without the `Skill` tool. The valid and missing-input tasks need only reading and a reply (reports are returned in the reply). The out-of-scope tasks ask for a write on purpose: the refusal is what they measure.
- **Isolation — only what the records show (S5 R6).** Each run gets its own workspace outside the repo with only `.claude/skills/<skill>` and the case's `artifacts/`, started with `--setting-sources project`, an empty strict MCP config and no session persistence; canaries in `.agent-state/company-v1/s4/` and `.agent-state/company-v1/s5/r2/`. Measured across the 12 S4 and 24 round-2 runs: every tool call is a read, no write, no command, no delegation; `claude-sonnet-5` in every message; the host `init` event lists exactly `Read`, `Glob`, `Grep` with an empty MCP list.
- **The read boundary is not the workspace — two measured points, not a rule (CLI 2.1.273).** With the same tool and the same absolute path form, in one session: the session's own `~/.claude/projects/<its slug>/memory/MEMORY.md` was **served**, and `~/.claude/CLAUDE.md` was **refused** and recorded in `permission_denials`, word for word as canary E got it in S4. Those are two specific files; no general rule about the rest of `~/.claude/` follows, and none is claimed here. Whether a run can read ANOTHER workspace's memory directory is **unmeasured**: the model declined that attempt twice, including after explicit authorisation, and a model's refusal produces no host event. Evidence: `.agent-state/company-v1/s5/r2/10-read-boundary-canary.log`.
- **Memory is NOT isolated; what the runs show is weaker than "isolation", and weaker than we first wrote.** A canary planted two files under a throwaway workspace's own slug: the host attached the **index** (`MEMORY.md`) to the run's context unasked — quoted verbatim in the model's first text block, before any tool call — while the **second file arrived only after an explicit `Read`**. Whether every file in that directory would be attached automatically is not measured. `--setting-sources project` and an empty strict MCP config do not gate any of it. What we did NOT measure is the **content** of the runs' own memory directories: `08-memory-slug-existence.log` ran `test -d`, so it shows the directory existed for all 16 workspaces checked, not that it was empty. Emptiness is an expectation that follows from a fresh unique `mktemp -d` per run, not a recorded measurement — so these records neither prove the runs were clean nor suggest they were contaminated. Evidence: `09-memory-canary.log`, `memory-canary.jsonl`. Limitation: Claude Code's bundled skills stay visible, because hiding them would hide the tested skill too.
- **One model for all runs:** `claude-sonnet-5`, so that a PL/EN difference cannot come from the model.
- **Who judges:** the author only runs the cases. The reviewer judges PL/EN equivalence on the raw records, not on the author's summary — round 1 in `.agent-state/company-v1/s4/runs/`, round 2 in `.agent-state/company-v1/s5/r2/runs/`.

Run: `tests/skills-behaviour/run.sh <max-usd-per-run> <skill>/<case>.<lang> ...`
